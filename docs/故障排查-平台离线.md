# RAgent 平台离线排查（2026-10-27）

> 现象：Pek.RPanlServer「服务器节点」显示某节点「离线」，但节点版本/资源数据还停在最后一次上报。
> 先别下结论说“RAgent 死了”——**平台离线只代表 WebSocket 心跳没上来**，进程可能还活着。

## 1. 30 秒区分：进程死了 / 进程活着但通道断了

在节点上执行（把 `<安装目录>` 换成实际目录，常见 `/www/Stardust/StarAgent`、`/opt/StarAgent`）：

```bash
# ① 服务状态（systemd 安装的情况）
systemctl status StarAgentRust --no-pager | head -20

# ② 进程是否存在、跑了多久
ps -eo pid,etime,rss,cmd | grep '[p]ek-ragent'

# ③ 本机控制接口是否还活着（有响应 = 进程活着）
curl -sS -m 5 http://127.0.0.1:5501/Ping; echo
curl -sS -m 5 http://127.0.0.1:5501/Info | head -c 300; echo

# ④ 平台通道日志（关键）
ls -lt <安装目录>/Log | head -5
grep -E '平台实时通道|WebSocket|panic|Upgrade|已由|服务启动|错误|error' <安装目录>/Log/*.log | tail -80

# ⑤ systemd 自己的记录（崩溃/被 OOM/被停止都能看到）
journalctl -u StarAgentRust --since '2026-10-26 17:00' --no-pager | tail -120

# ⑥ 是否被 OOM killer 杀过
dmesg -T 2>/dev/null | grep -iE 'oom|killed process' | tail -20
```

判定：

| ①/②/③ 的结果 | 含义 | 方向 |
|---|---|---|
| 服务 active，进程在，`/Ping` 有响应 | **进程活着，平台通道断了** | 看 ④ 的「平台实时通道已断开/连接失败」原因（网络、DNS、TLS、令牌、平台侧） |
| 服务 active，但进程不在 | 进程退出且 systemd 没拉起/正在拉起 | 看 ⑤ 的退出码、StartLimit、OOM；升级后未拉起也在此 |
| 服务 inactive/disabled | 服务被停/未安装/被禁用 | `systemctl enable --now StarAgentRust`；未安装则重跑 `install.sh` |
| `ps` 有进程但 `curl /Ping` 不通 | 进程卡死/端口被占/HTTP 线程死了 | 看日志与 `ss -lntp | grep 5501`；必要时重启服务 |

## 2. 常见根因

1. **手动 `nohup`/`&` 启动**：SSH 会话退出后进程被 SIGHUP 杀掉。必须用 `sudo sh install.sh` 注册 systemd（Windows 注册服务/计划任务）。
2. **升级后没拉起**：0.1.88 之前升级依赖 `execv`/重启助手/服务失败恢复；若服务未安装或 systemd 达到启动频率限制，就会停在离线。
3. **平台通道断开后监督任务卡死/panic**：0.1.88 之前没有 panic 日志、没有连接看门狗，可能“进程活着但永远离线”。
4. **OOM killer**：节点内存被其它应用吃满时，代理可能被优先杀；看 `dmesg`。
5. **网络/DNS/TLS**：节点出网被限制、平台证书/域名变化、代理环境变量；日志会写“WebSocket 连接失败/超时（第 N 次）”。
6. **令牌/配对失效**：平台删除节点、重置令牌、`Config/StarAgent.config` 里 `AutoUpgradeToken` 为空/不匹配；日志会写 401/403 或“等待批准”。

## 3. 0.1.88 的可靠性修复

- **panic 全局日志**：任何线程 panic 都写 `Log`（线程名/文件:行:列/消息），不再“进程活着但功能静默消失”。
- **平台通道自愈**：
  - 通道线程外层 `catch_unwind`，panic 后 5 秒重建运行时并重启；
  - 连接看门狗：180 秒仍未连上则重建 `WsClient`，防监督任务卡死导致永久离线。
- **systemd 服务单元**（DH.RustBase）：
  - `StartLimitIntervalSec=0`：禁用启动频率限制，崩溃后持续拉起，不会被 systemd 永久放弃；
  - `OOMScoreAdjust=-500`：降低代理被 OOM 杀掉的优先级。
  > 已装节点要**重新执行一次 `install.sh`**（或手工更新 unit 后 `systemctl daemon-reload`）才能拿到新单元；仅替换二进制不会改 unit。
- 升级路径保持：Unix `execv` 原地接管；Windows 服务失败恢复；兜底 `-ensure-running` 助手。

## 4. 本次节点（0.1.84，10-26 17:32 离线）建议动作

1. 按第 1 节确认是“进程死”还是“通道断”；
2. 如果是通道断/进程卡死：`systemctl restart StarAgentRust`，升级到 0.1.88，观察日志是否出现“平台实时通道连接中/已建立”；
3. 如果进程反复退出：把 `journalctl` 的退出码、`Log` 里 panic/错误段、`dmesg` OOM 段发我；
4. 如果服务未安装：`sudo sh install.sh`（会注册 systemd + 开机自启）；
5. 升级 0.1.88 后，平台仍离线但 `/Ping` 正常时，看日志里“平台实时通道”具体失败原因（现在会记录 URL 与错误，不再静默）。

## 5. 专项：日志反复出现「已有星尘代理实例运行（PID=xxx），本实例退出」

这是**单实例锁**在生效，不是崩溃：

```
已有星尘代理实例运行（PID=924），本实例退出：/www/StarAgent/Data/agent.lock
星尘代理启动（系统服务模式）...
```

systemd 每 5 秒拉起一个新实例，每个都看到锁里的 PID 仍然存活，于是主动退出 → 平台一直离线。

### 先确认 PID 是谁

```bash
ps -p 924 -o pid,ppid,etime,cmd
systemctl status 924 --no-pager | head -15
systemctl list-unit-files | grep -iE 'staragent|pek'
systemctl list-units --type=service | grep -iE 'staragent|pek'
cat /www/StarAgent/Data/agent.lock
```

三种常见情况：

1. **924 是遗留的旧 RAgent（手动启动/旧服务单元）**：两个实例抢同一个基础目录。  
   → 先停掉持有它的服务单元（`systemctl stop <旧单元>`），确认 924 退出；如仍不退再 `kill 924`，最后 `rm -f /www/StarAgent/Data/agent.lock`，`systemctl restart StarAgentRust`。
2. **924 是另一个 systemd 单元（旧 `StarAgent.service` 等）**：两个单元默认都开机自启。  
   → `systemctl disable --now <旧单元>`，只保留 `StarAgentRust`。
3. **924 是 nginx/sshd 等无关进程（重启后 PID 复用）**：旧锁文件残留。  
   → 0.1.90 起会自动识别“锁里的 PID 不是星尘代理”并清锁启动；旧版需手动 `rm -f Data/agent.lock` 后重启。

> 绝不要在**确认旧实例还活着**时直接删锁：会变成两个代理同时守护同一批应用，互相停/拉子服务。

### 0.1.90 的锁修复

- 锁内容改为 `PID + 程序路径`；
- 校验 PID 时增加**进程名判断**：PID 已被系统复用给其它程序（重启后常见）→ 自动清理残留锁；
- 拒绝启动时日志会带上持有者的**进程名与命令行**，不再只给一个 PID；
- 清理干净退出时按首行 PID 正确释放（兼容旧格式）。
