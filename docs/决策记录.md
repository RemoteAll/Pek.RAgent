## 2026-10-26（二）· 内存管理：系统缓存清理 + 虚拟内存在线配置

**用户原话**
- 「帮我加在线配置虚拟内存的功能，我发现当前服务器物理内存不够用了。」
- 「RAgent能像宝塔一样清理服务器的所有内存占用么？而不是只能针对自己本身的内存占用。」

**口径先说清（写进代码注释与面板文案）**
- Linux 上「释放内存」能安全回收的只有**页缓存/目录项/inode 缓存**（`sync` + `/proc/sys/vm/drop_caches=3`），这正是宝塔同类按钮的本质；
- **进程自己占用的匿名内存外部无法清理**，只能重启该进程（面板「进程 Top」定位 → 服务控制重启）；
- Windows 无等价接口（`EmptyWorkingSet` 只能针对单进程），故明确不支持而非假装成功。

**实施**
1. `src/memsys.rs`：`drop_caches()` —— root 校验 → 读 `MemAvailable/Cached` → `libc::sync()` → 写 `drop_caches=3` → 回读，返回前后对比；非 Linux 明确报不支持。
2. `src/swap.rs`：虚拟内存（Linux）在线配置
   - `status_json()`：套用 `dhrust::sys::machine::swap_info()`（总量/已用/条目/swappiness/平台能力）；
   - `create(path,size_mb,persist)`：`fallocate`（回退 `dd`）→ `chmod 600` → `mkswap` → `swapon`，失败逐级回收半成品；`persist` 写 `/etc/fstab`（先备份 `.pek-bak`，标记行 `# pek-ragent swap`）；
   - `remove(path)`：`swapoff`（600s）→ 删文件 → 清理 `fstab`；
   - `set_swappiness(0..=100)`：写 `/proc` + `/etc/sysctl.d/99-pek-swap.conf` 持久化；
   - 安全硬约束：仅 Linux + root；路径白名单目录（`/ /www /data /opt /var /home /mnt /media`）+ 字符白名单 + 禁 `..`；大小 128 MB~64 GB 且 ≤ 分区可用 90%；已存在文件/已启用 → 拒绝。
3. `dhrust::sys::machine::swap_info()`（公共库）：Linux 读 `/proc/meminfo` + `/proc/swaps` + `/proc/sys/vm/swappiness`；Windows 用 `GlobalMemoryStatusEx` 页面文件容量（只读）。
4. 面板：`/api/freeSystemMemory`（GET，PERM_CONTROL）、`/star/swapConfig`（POST，PERM_CONTROL，`action=create|remove|swappiness`）；`/star/machine` 新增 `swap` 字段；控制页加「🧹 清理系统缓存」按钮，机器页加「虚拟内存（Swap）」区块（表单 + 条目「关闭并删除」+ swappiness）。

**验证**：`cargo check` 无告警；`cargo test` **189 passed / 2 ignored**；`cargo clippy --all-targets` 零告警；`cargo zigbuild --release --target x86_64-unknown-linux-musl` 通过（50.6s，覆盖 Linux 专用分支）。

## 2026-10-26 · 常驻内存治理：UV 降级估算 + 流式聚合 + 释放内存真实生效

**用户原话**
- 「这个怎么显示占用四十多M的运行内存的」
- 「需要的，释放内存是空操作那不合理吧，而且目前是才启动状态」

**背景与诊断**
- 面板「进程」页内存列口径 = `ProcItem.memory_mb`，Linux 取 `/proc/<pid>/statm` 常驻页 × 页大小（**RSS**，不是虚拟内存）。
- 单文件 14.39 MB（Linux musl 静态）本身只解释几 MB；**「才启动就 46 MB」的主因在 weblog 启动回溯**：
  ① 首次读今天日志从文件头开始，全部 IP 塞进 `HashSet<IpAddr>`（原上限 100 万，约 20~35 MB）；
  ② `tick` 先把所有行收集成 `Vec<String>` 再收集成事件 `Vec`，几十 MB 日志瞬时堆膨胀；
  ③ 单块读取 8 MB，块内每行一个独立 `String`。
- 面板「释放内存」只调 `empty_working_set()`，而生产包是 musl——无 `malloc_trim`，代码里 `#[cfg(not(gnu))] { true }` 让面板把「什么都没做」显示成成功。

**决策与实施**
1. `weblog::UvSet`：精确 `HashSet` 上限 2 万条，超限自动降级 **HyperLogLog**（p=14，16384 寄存器 = 16 KB/集合，标准误差 ≈0.81%）；小站点仍精确，UV 仅展示用途。跨天/持久化口径不变（存 `uv_base + estimate`）。
2. `read_increment` 改**逐行回调**（`FnMut(&str, &mut Option<W3cFields>)`），`tick` 改为「读一块 → 解析一块 → 聚合一块」，取消事件全量缓冲与每行 site 克隆；`MAX_CHUNK` 8 MB → **1 MB**。
3. 新增 `weblog::release_caches()`：收缩 UV 精确集合、压缩站点/文件表容量（**不动**半行缓冲，避免丢行）。
4. `webpanel::free_memory` 重写：先清缓存再调平台回收，Linux musl 如实提示「当前平台无系统级回收接口」，不再假成功（始终 code=0，附 `clearedBytes/systemTrim/systemTrimSupported`）。
5. 公共库 `dhrust::sys::process`：`empty_working_set()` 在 musl 返回 `false`（真实语义），新增 `working_set_trim_supported()`（Windows EmptyWorkingSet / glibc malloc_trim 为 true）。

**验证**：`cargo check` 通过；`cargo test` **189 passed / 0 failed / 2 ignored**（新增 HLL 精度、UV 降级、UV 去重 4 项）；`cargo clippy --all-targets` 零告警。

## 2026-10-21 防重复影子实例 + RAgent 单实例锁

**用户原话**
- 「我看是在影子目录中执行的。那为什么还会经常性重启的？」
- 「服务器上只有一个RAgent，你也必须要防止这种问题啊，不可能会出现不应该活着的其他的进程啊」

**根因**
- 影子目录共用一个可执行文件；旧代理/旧版本遗留的 `dhdeploy-agent-rust.exe`（PID 33900）仍在运行并监听 8282/8283；
- RAgent 只跟踪当前 `Child`，不知道旧实例；新实例绑定 8282/8283 失败，`main` 监听错误分支 `exit(1)`；
- RAgent 每 30 秒守卫周期再拉，新实例继续失败，旧实例不死 → 无限重启循环。
- 应用日志看起来“退出后仍在写”，实际是多个实例写同一个日志文件；`实际运行=31s` 是 RAgent 的检测时间，不一定是新实例真实寿命。

**决策与实施（v0.1.50）**
- `AppRuntime::start()` 启动前扫描系统进程：
  - 精确匹配 `run_file`（规范化路径，Windows 大小写不敏感）；
  - 或匹配同一 `shadow_base` 下 `{app}-*` 目录中的进程（覆盖旧 MD5 影子路径）；
  - 多个匹配时优先保留有监听端口的，其次最早启动的；其余停止；
  - 保留者直接 `adopt`，**不再启动第二个实例**；任务模式不做接管。
- `run_core()` 增加 `Data/agent.lock` 单实例锁：`create_new` 原子创建；已有存活 PID 则拒绝启动并记日志；残留锁自动清理；正常退出释放。
- 回归测试：`shadow_matcher_covers_old_hashes_and_ignores_other_apps`、`same_exe_matches_current_process_binary`；**163 测试全绿**；Windows 包 `pek-ragent-v0.1.50-x86_64-pc-windows-msvc.zip`。

**运维止血**
1. 只保留一个 RAgent（停手动 `-run`/菜单实例，保留服务）；
2. 停 RAgent 服务，杀掉所有 `dhdeploy-agent-rust.exe`（含旧影子实例），再启动 RAgent；
3. 验证只有一个应用进程，且 8282/8283 的 PID 与 RAgent 最新启动 PID 一致。

## 2026-10-21 日志清理纳入 ProgramData 系统缓存（Windows）

**用户原话**
- 「`ProgramData`这个是不是日志清理时可以将这个中的该清理的也清掉。这个应该是windows的目录」
- 「这是服务器上文件管理中查看到的目录大小占用」（截图：`ProgramData` 5.43 GB、`Program Files (x86)` 7.01 GB、`Program Files` 3.89 GB、`Users` 26.39 GB、`pagefile.sys` 7.92 GB）

**决策与实现**
- 新增 Windows 分类 **「系统缓存」`system_cache`**：
  - `%ProgramData%\Microsoft\Windows\WER\ReportArchive|ReportQueue|Temp`（Windows 错误报告）
  - `%ProgramData%\USOShared\Logs`（更新会话编排日志）
  - `%ProgramData%\Microsoft\Windows\Caches`（图标/缩略图缓存，系统按需重建）
  - `%ProgramData%\Temp`、`%SystemRoot%\Temp`（系统与第三方临时文件）
- 「系统日志」补 `%SystemRoot%\Logs\WindowsUpdate`（原仅 CBS/DISM）。
- 路径改由 `%SystemRoot%` / `%ProgramData%` 解析（回退 `C:\Windows` / `C:\ProgramData`），兼容系统盘非 C:。
- **有意不含**：`ProgramData\Package Cache`（VC++/VS 安装缓存，删除会导致修复/卸载失败）、Windows Defender 定义库、`AppRepository`、`SystemData`——测试 `windows_system_cache_targets_stay_within_safe_dirs` 断言排除。
- 实测（本机隔离实例 5599）：`system_cache` 扫出 177,385,453 B（`USOShared\Logs` 93.1 MB + `Windows\Temp` 80.5 MB + WER 2.8 MB + Caches 1.0 MB）；`system` 29,361,750 B（含 `WindowsUpdate` 20.9 MB）；**165 测试全绿**。
- 待办：服务器 `ProgramData` 5.43 GB 的大头需先逐目录定位（常见大户：`Package Cache`、`Microsoft\Windows Defender`、`Microsoft\EdgeUpdate\Download`、`ClickToRun`、数据库数据目录），确认后再决定是否把安全项加入分类；`Package Cache` 即使占用大也不默认清理。

**运维排查命令（服务器 PowerShell，列出 ProgramData 一级目录占用前 20）**
```powershell
Get-ChildItem 'C:\ProgramData' -Directory -Force -ErrorAction SilentlyContinue | ForEach-Object { $s=(Get-ChildItem $_.FullName -Recurse -File -Force -ErrorAction SilentlyContinue | Measure-Object Length -Sum).Sum; [pscustomobject]@{ Dir=$_.Name; MB=[math]::Round($s/1MB,1) } } | Sort-Object MB -Descending | Select-Object -First 20
```

## 2026-10-21 日志清理安全审计（确保不会导致系统问题）

**用户原话**
- 「要做审计，鹕保最新的清理不会导致系统问题」（意为“确保”）

**审计发现的真实风险（已全部修复）**
1. **自定义路径无护栏（高危）**：`LogCleanupPaths` 原可填 `C:\Windows`、`C:\ProgramData`、任意系统文件 → 目录被递归清空 / 文件被截断。现 `deny_reason()` 统一守卫：
   - 根目录/盘符根、相对路径一律拒绝；
   - Windows：`%SystemRoot%` 本身、`System32/SysWOW64/WinSxS/servicing/Fonts/assembly/Microsoft.NET/Boot`（整树）、`Program Files`/`Program Files (x86)`/`ProgramData`/`Users`（本身+一级子目录，`temp/tmp/logs/log/cache/caches` 类白名单放行）、系统盘 `PerfLogs/Recovery/boot/config.msi/$Recycle.Bin/System Volume Information`（整树）；
   - Unix：`/etc /usr /bin /sbin /lib /lib64 /boot /proc /sys /dev /run /var/lib /var/spool`（整树）、`/var /root /home /opt /srv /mnt /media /snap`（本身）；
   - 程序目录：本身与上级拒绝，内部**仅允许 `Log` 子目录**（防清掉 `Config/Data/Plugins`）；
   - 保存接口写配置时即 400 拒绝；扫描接口新增 `warnings` 数组返回被拒的自定义项。
2. **符号链接/目录联接会被跟随（中危）**：递归清理现统一 `symlink_metadata` 判断——**链接既不进入也不删除**；顶层目标本身是链接时直接跳过并报错（`dir_stats_limited` 同步跳过，统计与清理一致）。
3. **超大目录无上限（中危）**：原递归无条目/时长限制，`C:\Windows\Temp` 数十万文件时长时间占用磁盘与请求线程。现 `ClearLimits`：20 万条目 / 120 秒上限，超限停止并记日志。
4. **单条目失败中断整目录（低危）**：原 `?` 让一个被占用文件终止整个目录清理；现改为记录（最多 20 条）后继续，仅读目录失败才返回错误。
5. **清理阻塞 HTTP 线程（中危）**：清理改在独立线程 `ragent-logclean` 执行后 join，避免面板其它请求卡死；线程创建失败回退同步执行。

**验证**
- 单测：logclean 14 项（新增 5 项守卫/链接/限流用例）；全量 **170 通过 / 0 失败**；`logclean.rs` clippy 零告警（其余 69 条为 agent/app/cli 历史告警，非本轮引入）。
- 端到端（隔离实例 5599）：`C:\Windows`、`C:\ProgramData`、`C:\Windows\System32`、`C:\Users\Public`、`C:\ProgramData\Microsoft` 均返回 `code=400 不允许的清理路径…`；`C:\Windows\Logs\CBS` 允许（内置日志目录）；合法自定义目录扫描 1500B → 清理 `freed=1500 files=2`（`.log` 截断为 0、`.tmp` 删除、`errors=0`）。
- **排查坑**：dhrust `json_error` 返回 **HTTP 200 + body `code`**——冒烟判断必须看 `body.code`，不能看 HTTP 状态码。

## 2026-10-21 文件管理在线编辑上限调整与提示优化

**用户原话**
- 「而且怎么超过 2M 都会提示文件过大的？」（点击 24.57MB 的 `tmpXXXXXX.tmp` 后再编辑弹“文件过大（上限 2MB），请使用下载或 SFTP”）
- 「这个 2M 文件太小啊，而且你不是应该也要给我在清理时将这些该清理的文件给清除掉吧」
- 「这种不能小于 10M 吧」

**决策与实现**

## 2026-10-22 数据库访问按最新 Pek.RCode 规范调优（流量归档 / 过期清理）

- **用户原话**：「RAgent是不是也可以考虑接入最新的Pek.NCode并分析判断是否也可以调优数据库相关」

### 一、现状核实

- `pek-rcode` 依赖已指向 `../Pek.RCode`（最新主干），本轮无需改依赖。
- 生产路径的数据库操作只有三处：`upsert_by_key`（归档写）、`entity_cache`（面板读整表）、
  过期清理（查 Id 后逐条 `delete_by_pk`）。读路径已是最优（整表缓存 + 写自动失效）。

### 二、发现并修复的两个热点

| 位置 | 原实现 | 改后 | 效果 |
|------|--------|------|------|
| `update_web` / `update_ports`（每 30 秒归档一次） | 逐行 `upsert_by_key`＝每行 **1 次 SELECT + 1 次写**，共 `2N` 次往返 | 先**一次查询**取当日 `(Id, 自然键)` 建索引 → 命中行 `update_by_pk` → 新增行合成**一次 `insert_batch`** | 往返 `2N → 1 + K + 1`；**跨天首次归档只需 2 次** |
| `maybe_prune`（每日清理） | `query` 取 Id 列表后**逐条** `delete_by_pk`（最多 10 万次往返） | 单条 `delete_where_batched`（引擎分块 `DELETE ... WHERE ...`） | N 次往返 → 分块删除，日志由「查询失败/逐条失败」简化为一条失败 |

> 说明：表是 `Id` 自增主键 + `StatDate|Site`／`StatDate|Proto|Port` 自然键（**无唯一索引**），
> 因此不能用 `write_batch(Upsert)` 的 `ON CONFLICT`；采用「索引 + 按主键更新 + 批量插入」达到同等收益。

### 三、基准（`bench_archive_roundtrip`，`#[ignore]`）

`cargo test --release bench_archive_roundtrip -- --ignored --nocapture`
（20 轮 × 30 站点 + 150 端口，本地 SQLite）：

| 实现 | SQL 次数 | 耗时 | 每轮 |
|------|---------|------|------|
| 旧（逐行 upsert） | ~7 200 | 135.5 ms | 6.78 ms |
| 新（索引 + 批量） | ~3 640 | 82.4 ms | 4.12 ms |
| **加速** | −49% | **1.64x** | — |

本地 SQLite 每次往返极便宜，1.64x 已是「纯往返」收益的体现；若改配远程库（MySQL 走组件驱动），
每次往返含网络 RTT，收益会明显放大。归档是 30 秒一次的常态动作（守护进程长期运行），
此优化直接降低日常 I/O 压力。

### 四、回归与正确性

- 新增 `batch_archive_matches_rowwise_upsert`：同一数据集分别走「批量」与「逐行 upsert」，

## 2026-10-24（三）· 站点信息上报时机与心跳盘点缓存

### 一、用户原话

> 「这个是RAgent定时经常上报每个节点的站点信息么？」

### 二、现状（回答）

- **心跳每 60 秒一次**（`panel_ws::build_heartbeat`），报文里带 `sites` 站点摘要
  （key/kind/name/domains/ssl/managed）——这是最频繁的上报。
- 另外三个时机都是**实时**：① Agent 上线 2 秒后主动推一次 `siteInventory`；
  ② 平台点「🔎 让节点重新盘点站点」→ `siteScan`；③ 打开节点面板「🔐 证书」页 → `/star/sites`。
- 实测（本机 50 个站点、其中 25 个带证书）：一次完整盘点 **21~57 ms**（首次含文件系统预热），
  报文约 8 KB。即每分钟约 20 ms 磁盘/CPU，占单核 0.04%。

### 三、优化（心跳不再每次全量盘点）

- 新增 `sites::inventory_cached()` / `summary_cached()`：**按签名缓存**，
  签名 = 各 nginx 配置文件的「路径 + 长度 + mtime」+ `CertManagedSites` + `CertNginxDirs/Bin`

- 签名不变且未超 300 s TTL → 直接复用上次结果（心跳只做几十次 `metadata()`，不再读配置、不再解析 X.509）。
- 签名一变（改站点配置 / 勾选白名单 / 加目录）→ **立即重新盘点**，不会等 TTL。
- `certAllow` / `certDeny` / `certConfig` 保存后调用 `invalidate_cache()` 兜底即时生效。
- 面板 `/star/sites` 与平台 `siteScan` **仍走实时** `inventory()`（用户主动要看最新）。
- 新增单测 `inventory_cache_invalidates_on_change`：缓存命中、白名单变化立即生效、新增站点文件立即生效。

### 二、证书剩余天数口径统一（99% 是口径差，不是两张证书）

同一张证书、同一时刻，三处显示不同，根因是**取整方式不同**（证书 `not_after = 2027-01-24 08:51:48 UTC`，

| 口径 | 结果 |
|---|---|
| 旧实现（`(secs + 86399)/86400`，向上取整） | **93 天** ← 平台/Agent 旧值 |
| 宝塔面板（不含今天、按完整天数） | **91 天** |
| 新实现（`div_euclid(86400)`，向下取整） | **92 天** |

- `dhrust::cert::CertInfo::days_left` 改为**向下取整**（不足一天不计），平台 `certs::Cert::to_json` 同步；
  与 nginx/宝塔的保守口径一致，杜绝「显示还有 1 天其实已过期」的错觉。
- **以到期日期为准**：Agent 面板「现有证书」列新增 `至 2027-01-24 UTC · <SHA1 前 12 位>`，

## 2026-10-24（六）· 在线终端：新连接自动显示服务器概况（Linux / Windows / IIS）

### 一、用户原话

> 「RAgent在线终端每次新连接时或者反正就是第一次时是不是要先自动执行获取当前服务器的信息，windows和iis等都要支持。」

### 二、实现方式（不往 shell 注入命令）

- 新增 `GET /star/termBanner`（`terminal` 权限）：本机采集并返回一段概况文本。
  **不执行、不注入任何 shell 命令**——Linux 的 bash 与 Windows 的 PowerShell/cmd 表现一致，也不污染命令历史。
- 内容：主机名 / 系统与架构 / CPU（核数·型号·Linux 负载）/ 内存 / 磁盘（前 3 个）/ 网络（首个已连资产 IPv4）/

- 前端 `termInit` 首次进终端时取一次（失败不阻断），**在 PTY 初始输出静默后**写入（`termScheduleBanner`：
  onopen 起 700ms、每收到输出重置为 450ms）。

### 三、踩坑（关键）

1. **不能在 WS 首帧发 banner**：PTY 的启动输出（提示符/欢迎语）随后到达，banner 会被夹在中间。
2. **不能 `reset()` 后立刻写**：xterm 的 reset 与 write 是异步队列，顺序不可控。
3. **ConPTY（Windows）启动会发 `\x1b[2J` 清屏序列**——回放里就带着它，banner 早写会被整屏擦掉。
   最终方案 = **等 PTY 输出静默后再写**，顺序自然变成「欢迎语 + 提示符 → 概况」，等于在终端里自动跑了一条信息查询命令。
4. xterm 只渲染可视区，`innerText` 断言只能看到当前屏；验证要看实际写入序列（临时包一层 `write` 记录）。

> 目前可以让RAgent支持导入Rust和C#的包自动安装部署么？我记得RAgent可以在web界面导入安装的？是压缩包中也需要脚本还是什么样的？
> 这个是只管安装到Pek.RAgent中，不考虑C#版本，因为后续会逐步替代，而且我也想考虑是不是有自动做迁移的，把C#版本中的迁移过来并把C#版本中的停掉
> 而且我要的是在web上新安装，不是通过ssh安装，因为后续不提供ssh给到别人

**结论与实现**

1. **口径**：应用安装只面向 Pek.RAgent，主路径是 Web 面板（📦 上传应用包 / 拖拽，包内不需要脚本，
   `apppkg.rs` 只做“解压→识别主程序→落工作目录→影子注册→启动”）；C# 版只做“迁移”，不再提供新增安装；
   `packaging/install-app.sh` 降级为无面板/批量自动化兜底，并去掉 C# 自动注册话术。
2. **新增 `src/migrate.rs`**：
   - `scan`：**只读**解析 C# 的 `Config/StarAgent.config`（不生成/不补齐/不写盘），读取原始
     `ServiceName`/`LocalPort`（缺省 `StarAgent`/5500），返回子服务清单、服务已安装/运行状态与告警；
   - `migrate`：① 经 C# 本机 UDP RPC（`dhrust::net::api_rpc::stop_service`，与 C# `StarService.StopService`
     同一契约，无需 C# 命令行交互）逐条停 C# 子服务；② 停并（默认）**禁用** C# 星尘系统服务
     （`sc stop` / `sc config start= disabled`；Linux `systemctl stop/disable`），非服务形态时结束其进程；
     ③ 相对路径按 C# 安装目录**绝对化**（程序与数据不搬家，只换“谁来守护”）；④ 导入配置
     （C# 数值模式 10-13 归一化为 `shadow/standard/hosted/task`）；⑤ 启动启用条目；
   - 防呆：源目录 = 当前安装目录 → 直接拒绝；C# 服务名 = 当前服务名 → 跳过停服；RPC 不通 → 告警并继续；
   - `detect` 排除含 `<AgentId>` 的 Rust 版自身配置（避免弹出“迁移自己”的提示条）。
3. **面板**：`GET /star/starAgentScan?dir=`（预览；未找到返回 `found=false` + 常见路径候选）、
   `POST /star/starAgentMigrate?dir=&names=&stopApps=&stopService=&disableService=&startApps=`；
   权限 `services`，审计动作「扫描 C# 星尘 / 迁移 C# 星尘」。子服务页新增「🔄 迁移 C# 星尘」按钮，
   自动检测提示条每次进入只探测一次（不随 3 秒轮询扫盘）。
4. **验证**：
   - `cargo test` **199 passed / 2 ignored**（新增 6 项迁移单测：扫描、路径绝对化、导入不启动、
     UDP RPC 停服、自目录拒绝、无配置拒绝）；
   - 冒烟 `scripts/_smoke-migrate.ps1`（隔离实例 5598）**25 项全过**：扫描/预览/导入/幂等重导/
     空目录与未勾选用例/停服快速返回；
   - 浏览器实测（隔离实例 5598）：按钮 → 弹窗 → 扫描（2 条 C# 子服务，模式显示 standard/shadow 正确）
     → 迁移 → toast「迁移完成：导入 2 个子服务」+ 列表出现 `demo-agent`（启用）/`dotnet-app`（禁用）。
   - 顺手修复 0.1.84 遗留：`/api/status` 未下发 `memoryFreeMB`/`memoryCachedMB`（内存卡「缓存/空闲」
     恒为 0，clippy 两处 unused 告警），现按 Linux `MemFree` / `Cached+SReclaimable` 口径下发。
5. **已知边界**：C# 与 Rust 服务同名时跳过停服（需人工确认后再停 C#）；RPC 不通时 .dll 托管的
   dotnet 应用无法按路径精确结束（仅能结束同名 exe），需在原 C# 面板手工停止后再迁移。
