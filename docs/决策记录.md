## 2026-10-20 网站流量：IIS 站点全量 / 状态 / 在线启用 sc-bytes

**用户原话**
- 「这个网站流量这里的站点肯定不对，服务器上肯定不只这一个默认的」
- 「而且页面底部的那个时间也不对」
- 「那是否可以在网站流量这里操作让勾选 `sc-bytes`，而且网站是启用还是禁用的状态是否也能有」

**决策与实施**
- IIS 站点发现改为继承 `applicationHost.config` 的 `siteDefaults`、展开 `%VAR%`、读取共享配置 `redirection.config`；**全部站点返回**，无日志/非 W3C 的站点附原因，不再只显示 Default Web Site。
- 新增 `POST /star/webLogFix`（`config` 权限）：可对单站点或全部 IIS 站点启用日志并勾选 `sc-bytes`；修改前备份 `applicationHost.config.pek-bak`，站点名含单引号拒绝；成功后触发站点重新发现。
- 面板站点表增加运行状态（Started/Stopped）、日志启用状态与操作列；W3C 解析兼容旧 `#Fields` 头 + 行尾新增 sc-bytes 列。
- 页脚时间改为服务器 `localTime` 锚点（UTC 方法计算），不再显示浏览器本机时间。
- Windows 端口视图无字节计数：显示 `—` 并明确提示，不伪造 `0 B/s`。
- 版本 **v0.1.46**；Windows/Linux 全平台包已重出。

## 2026-10-21 端口流量：显示占用应用与完整路径

**用户原话**
- 「会不会是8282和8283这两个端口号被占用了？能不能在我截图这里将占用的应用名和所在路径显示出来？」

**决策与实施**
- `portstat` 的 `ViewEntry/Row` 增加 `pid/process/path`；Windows 从 `GetExtendedTcpTable/GetExtendedUdpTable` 的 `dwOwningPid` 取 PID（TCP 优先 LISTEN 行），再用 `QueryFullProcessImageNameW` 取进程名与完整路径；`/star/portTraffic` JSON 输出 `pid/process/path`。
- 前端端口表新增「应用（PID）」「路径」两列；路径列自动换行，避免撑破表格。
- Linux `/proc/net/*` 连接视图没有 PID，暂显示空白（本次只覆盖用户当前 Windows 场景）。
- 版本 **v0.1.49**；用该功能确认 8282/8283 的占用者是 `dhdeploy-agent-rust.exe` 的**旧影子实例**（PID 33900），不是外部程序。

## 2026-10-21 退出诊断：先看退出码，不猜

**用户原话**
- 「如果判断信息不够，那就加日志」
- 「怎么感觉你这在乱搞，DHDeploy在Linux都是能正常运行的，你现在这样改的目的是什么？」

**决策与实施**
- RAgent 增加诊断日志：`handle=Owned/Adopted`、独立 `is_alive(PID)`、实际运行时长、`errorCount`、退避/守卫周期、显式重启原因（v0.1.47）；随后增加 `ExitStatus` 退出码（v0.1.48）。
- 线上实测：`handle=Owned`、`is_alive=false`、`process=-`、`exit code: 1（0x1）`；应用确实退出，不是 RAgent 的 `has_exited` 误判；30 秒节奏来自 RAgent `GuardPeriod=30000ms`，不是应用运行 30 秒。
- **教训**：应用侧（DHDeploy.Agent.Rust）的 panic hook、心跳、任务完成等诊断改动属于过度修改，已全部回退；**Linux 正常说明业务逻辑没问题，不能先改应用代码**。后续只在证据指向的具体链路加最小日志。
- **教训**：用户反复提供的日志要按时间线对齐看，不要重复索要。

## 2026-10-21 防重复影子实例 + RAgent 单实例锁

**用户原话**
- 「我看是在影子目录中执行的。那为什么还会经常性重启的？」
- 「服务器上只有一个RAgent，你也必须要防止这种问题啊，不可能会出现不应该活着的其他的进程啊」

**根因**
- 影子目录共用一个可执行文件；旧代理/旧版本遗留的 `dhdeploy-agent-rust.exe`（PID 33900）仍在运行并监听 8282/8283；
- RAgent 只跟踪当前 `Child`，不知道旧实例；新实例绑定 8282/8283 失败，`main` 监听错误分支 `exit(1)`；
- RAgent 每 30 秒守卫周期再拉，新实例继续失败，旧实例不死 → 无限重启循环。
- 应用日志看起来“退出后仍在写”，实际是多个实例写同一个日志文件；`实际运行=31s` 是 RAgent 的检测时间，不一定是新实例真实寿命。

**决策与实施（v0.1.50）**
- `AppRuntime::start()` 启动前扫描系统进程：
  - 精确匹配 `run_file`（规范化路径，Windows 大小写不敏感）；
  - 或匹配同一 `shadow_base` 下 `{app}-*` 目录中的进程（覆盖旧 MD5 影子路径）；
  - 多个匹配时优先保留有监听端口的，其次最早启动的；其余停止；
  - 保留者直接 `adopt`，**不再启动第二个实例**；任务模式不做接管。
- `run_core()` 增加 `Data/agent.lock` 单实例锁：`create_new` 原子创建；已有存活 PID 则拒绝启动并记日志；残留锁自动清理；正常退出释放。
- 回归测试：`shadow_matcher_covers_old_hashes_and_ignores_other_apps`、`same_exe_matches_current_process_binary`；**163 测试全绿**；Windows 包 `pek-ragent-v0.1.50-x86_64-pc-windows-msvc.zip`。

**运维止血**
1. 只保留一个 RAgent（停手动 `-run`/菜单实例，保留服务）；
2. 停 RAgent 服务，杀掉所有 `dhdeploy-agent-rust.exe`（含旧影子实例），再启动 RAgent；
3. 验证只有一个应用进程，且 8282/8283 的 PID 与 RAgent 最新启动 PID 一致。
