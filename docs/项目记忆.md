## cpu-percent-fix.md

# CPU 百分比恒为 0 的修复（2026-10-20，Agent v0.1.36）

- 用户反馈：「Cpu好像没有拿到数据」→「要等一会儿才会有变化。」
- 根因（dhrust `sys::monitor::update_cpu_percent`）：无论是否真的算出结果都会推进采样基线
  （`LAST_CPU` 的 at/cpu）。面板一轮刷新打多个接口（machine / services / getProcessList），
  后到的调用把基线顶到 now → 差分窗口永远 < 200ms → 走「复用上次结果」分支 →
  一旦上次是 0 就自我复用锁死在 0，只有碰巧间隔久一点才有值。
- 修复：间隔 < 200ms 时复用上次结果，但**基线原样放回不推进**；只有真正完成一次
  ≥200ms 的差分计算才推进基线。任何高频调用方都不再污染下一次有效采样。
- 验证：新增单测 `short_interval_call_does_not_advance_cpu_baseline`；
  基准里连打 10 次后隔 1.2s 取值，实测 `Code 87.98% / WmiPrvSE 61.59% / WXWorkWeb 40.22%`
  （修复前同场景全 0）。
- 通用教训：**任何「差分型」指标（CPU% / 速率）的基线只能在真正完成计算时推进**，
  否则高频空转调用会让指标永久为 0。

## portstat 要点

- Linux nft：独立表 `inet pek_stats`（priority -350；policy accept 只计数不动转发）；规则 comment `pek-in-tcp-80`；读取 `nft -j list table`（解析匿名 counter）；按 handle 删；**表跨重启保留**（计数不丢）；`PortTraffic` 关闭/卸载时 drop（cli.rs `cmd_uninstall` → `portstat::cleanup`）
- 端口集合：配置优先；空=监听端口（/proc/net tcp LISTEN + udp 未连接），上限 64；规则=端口×2 协议×2 方向
- 连接视图：/proc/net/*（Linux，UDP 跳过已 connect socket）；Windows GetExtendedTcpTable/UdpTable（端口字段=低 16 位 swap_bytes）
- 行数上限 150（排序后截断，防 UDP 临时端口噪音）；降级后每 5 分钟重试恢复 nft
- 速率：5s 差分

## proc-table-layout.md

# 进程表排版修复（2026-10-20，Agent v0.1.35）

- 用户原话：「这个排版有问题，不是应该进程 / 可执行文件这一列自动换行就好了么」。
- 根因：进程表沿用 `.info-table` 通栏规则（`td:first-child{width:200px}` +
  `td:last-child{word-break:break-all}`）→ PID 列吃掉宽度、末列「启动时间」被强制断行，
  窗口一窄就变成一列一个字。
- 改法：进程表单独用 `.proc-table` 类：
  - PID / 用户 / CPU / 内存 `width:1%`（收到最窄，不撑表）；
  - **「进程 / 可执行文件」列承载剩余宽度并自动换行**（`word-break:break-all`，去掉 nowrap/ellipsis）；
  - 监听端口逐个 `inline-block` span，列窄时自动换行；
  - 启动时间拆两行（日期 10px + 时间 10px 灰字）；
  - 表格 `min-width:640px`，路径列 `min-width:120px`。
- 验收：临时静态预览页 + 浏览器实测，660px 极窄容器下各列 `scrollWidth == clientWidth`
  （无裁字、无竖排），路径正常折行；真实面板更宽，路径列自动扩展到几百 px。
- 教训：给「通用表格」加新列前先看它是否继承 `.info-table` 的首/末列规则，
  多列表格应使用独立 class 覆盖（否则新列会破坏既有列宽分配）。

## proc-top.md

# 进程 Top 字段（2026-10-20）

- `dhrust::sys::monitor::ProcItem`：`name/pid/memory_mb/threads/cpu_seconds` + `cpu_percent/user/exe/command/cwd/handles/start_time`。
- CPU%：两次调用差分，占**单核**可 >100；`Δt < 200ms` 时**复用上次 percent**（否则连续调用全 0）；首次为 0。
- 性能：先全量取轻字段（Linux stat/statm、Windows Toolhelp）排序，只对返回的前 N 补重字段。
- Linux 重字段：`/proc/{pid}/{exe,cwd,cmdline,fd}` + `status` 的 `Uid`→`/etc/passwd`（缓存）；启动时间 = `btime + starttime/CLK_TCK`。
- Windows 重字段：`QueryFullProcessImageNameW`、`GetProcessHandleCount`、`GetProcessTimes`（启动时间）、`OpenProcessToken`+`LookupAccountSidW`（用户名）；无 PEB 读取 → `command` 用 exe 路径、`cwd` 空。
- RAgent：`/star/machine` 返回「CPU Top20 ∪ 内存 Top20」；`/star/getProcessList?sort=cpu|memory&count=N`（N ≤ 300）；前端进程表 7 列可切换排序。
- 验证：Windows 冒烟 `rows=32 withExe=31 withUser=31 maxCpu=91.3`（Code 91.3% / WmiPrvSE 52.4%）；`cargo zigbuild --target x86_64-unknown-linux-musl` 通过。

## watchdog.md

# 子服务假死自愈（2026-10-20）

- 症状：RAgent 面板显示「运行中」，但子服务（如 DHDeployRust）请求全无响应；重启 RAgent 才恢复。
- 根因：守护循环只判 PID 存在；`HealthCheck` 只在启动时探一次且失败仅记日志。
- 现实现（`app.rs::check_health`，每 `GuardPeriod` 一轮）：
  - 连续 3 次失败（`HEALTH_FAIL_LIMIT`）→ 停止 + 按 `Delay` 重启；启动宽限 `max(StartWait,5s)`。
  - `HealthCheck` 取值：
    - 空 → 自动发现该进程（含子进程树）TCP LISTEN 口（Linux `/proc` fd→socket inode↔`/proc/net/tcp`；Windows `GetExtendedTcpTable`）+ 宽松探活（写 HTTP 请求，3s 无任何字节 = 假死）。
    - `http(s)://` / `tcp://` → 显式。
    - `file:<路径>[?within=秒]` → 文件活性（mtime+size 无变化）。
    - `heartbeat[?within=秒]` → `POST /star/appHeartbeat?name=`；**从未上报不判定**（不支持则不探）。
    - `off`/`none` → 关闭。
- 原则：拿不到活性信号就不判定（防误杀纯计算型/空闲服务）。
- 面板：`/star/services` 返回 `Health`(off/ok/warn/fail)/`HealthFails`/`HealthError`/`HealthOkAt`/`LastHeartbeat`。
- 测试：`app::tests` 5 项（含「只 listen 不 accept」假死模型）。

- 根因：WAF 页容器只用了 `class="card"`（仅有内边距），其它配置卡是 `class="glass-card card"`；
  卡片背景/边框/圆角/阴影全部来自 `.glass-card`，所以安全页看起来是“裸排版”。
- 修复：两处 WAF 卡片改 `glass-card card`，标题由 `h3` 改为与其它配置卡一致的 `h2`。
- 验证：隔离实例 computed style 确认背景 `rgba(255,255,255,.55)`、1px 边框、14px 圆角、卡片阴影；
  截图与 Agent 配置/星尘设置卡片一致。

## IIS w3wp 进程应用路径识别（2026-10-20）

- 用户：「像这种都是获取不到实际的应用路径的么？这种一般都是IIS运行的吧」→「需要的」。
- 新增 `src/iis.rs`：`w3wp.exe` 通过 `NtQueryInformationProcess(ProcessCommandLineInformation)`
  读取 `-ap` 应用池（不读 PEB、不启子进程），解析 `applicationHost.config`（60 秒缓存）
  映射应用池 → 站点/应用物理路径；命令行失败时回退用进程用户（`IIS APPPOOL\Pool` / `Pool`）匹配。
- 进程 JSON 新增 `appPool`/`iisSites`；有映射时 `app`=站点名、`appPath`=物理路径；
  多应用共用应用池时显示“首个站点 等 N 个应用”，路径以 `；` 连接；前端 tooltip 展示应用池与各站点路径。
  非 Windows / 非 IIS 环境完全回退原有行为。
- 测试：`cargo test` **147 passed / 1 ignored**（含 Windows 实机命令行读取、applicationHost.config 样例解析、用户回退）。
  本机无 IIS，真实站点映射需在有 IIS 的 Windows 机器部署后验证。

## IIS 网站流量接入 + 敏感配置下线（2026-10-20）

- 用户：「这里是获取不到IIS的网站流量等数据是吧？另外配置中的这些是不是也可以不需要在线填写，我怕被人改乱。」
- IIS 网站流量：`discover_sites()` 在 Windows 改走 `iis::discover_log_sites()`——解析
  `applicationHost.config` 的站点/`<logFile directory>`（默认 `%SystemDrive%\inetpub\logs\LogFiles\W3SVC<id>`），
  取各站点最新 `.log` 文件；`weblog` 新增 W3C 解析（`#Fields:` 头、`sc-status`/`sc-bytes`/`c-ip`，
  无头时回退 IIS 默认字段序）。**IIS 默认日志字段不含 `sc-bytes`，未启用时只能统计请求数/UV/状态码，流量为 0**。
- 敏感配置下线：`PluginStoreUrl` / `PluginStorePubKey` / `AutoUpgradeUrl` / `AutoUpgradeIntervalMinutes` /
  `AutoUpgradeToken` 从 `config_metadata` 移除，且 `apply_config_value` 拒绝这些键（即使直接调 `/api/updateConfig` 也改不了）；
  只能编辑服务器 `Config/StarAgent.config`；配置页增加提示。平台下发分发源（`panel_ws`）不受影响。
- 验证：`cargo test` **152 passed / 1 ignored**（含 W3C 样例、日志目录映射、敏感键拒绝）、`node --check web/app.js`；
  本机无 IIS，真实 IIS 日志需在启用 `sc-bytes` 的 Windows 服务器上部署后验证。
