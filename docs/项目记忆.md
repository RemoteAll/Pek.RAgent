## cpu-percent-fix.md

# CPU 百分比恒为 0 的修复（2026-10-20，Agent v0.1.36）

- 用户反馈：「Cpu好像没有拿到数据」→「要等一会儿才会有变化。」
- 根因（dhrust `sys::monitor::update_cpu_percent`）：无论是否真的算出结果都会推进采样基线
  （`LAST_CPU` 的 at/cpu）。面板一轮刷新打多个接口（machine / services / getProcessList），
  后到的调用把基线顶到 now → 差分窗口永远 < 200ms → 走「复用上次结果」分支 →
  一旦上次是 0 就自我复用锁死在 0，只有碰巧间隔久一点才有值。
- 修复：间隔 < 200ms 时复用上次结果，但**基线原样放回不推进**；只有真正完成一次
  ≥200ms 的差分计算才推进基线。任何高频调用方都不再污染下一次有效采样。
- 验证：新增单测 `short_interval_call_does_not_advance_cpu_baseline`；
  基准里连打 10 次后隔 1.2s 取值，实测 `Code 87.98% / WmiPrvSE 61.59% / WXWorkWeb 40.22%`
  （修复前同场景全 0）。
- 通用教训：**任何「差分型」指标（CPU% / 速率）的基线只能在真正完成计算时推进**，
  否则高频空转调用会让指标永久为 0。

## iis-appcmd-idempotent.md

# IIS 部署 appcmd 幂等坑（2026-10-22 现场）

## 现象
DHDeploy 部署 Windows/IIS 节点报：
```
部署失败：appcmd 执行失败（退出码 1）：<?xml version="1.0" encoding="UTF-8"?>
<appcmd>
</appcmd>
```
日志里紧跟 `[IIS] 部署未正常完成，已恢复站点 <站点>`（说明 start 第二次成功）。

## 第二处（真正的元凶，2026-10-22 复测）
`appcmd list wps /apppool.name:<池> /xml` 在**没有 worker**（应用池已停，正是部署流程停池之后的常态）
同样返回 **退出码 1 + 空 `<appcmd></appcmd>`** → `workers_of_pool` 报错 → `kill_pool_workers` 把 `stop()` 整个打断。
**修复**：`workers_of_pool` 改为**进程快照 + 命令行 `-ap "池名"` 归属**（新增 `monitor::pids_by_name`，
Toolhelp / /proc），appcmd 仅作交叉验证；新增 `appcmd_raw` 与 `is_empty_appcmd_doc`。
教训：**appcmd 的「空结果」普遍是 exit 1 + 空文档**（list wps / list site 等），不能按退出码判定失败。

## 根因（第一处）
`appcmd stop/start site|apppool` 对「目标已处于期望状态」会返回 **退出码 1 + 空 `<appcmd></appcmd>`**。
旧实现用 `site_states()`/`app_pool_states()`（批量 + 15s 缓存）做幂等预判，缓存/时序不准时误判未达状态 → 执行命令 → 失败即报错。
典型：`start apppool` 时池已被 WAS/站点带起 → `state:"Started"` 但缓存里是 Stopped。

## 修复（dhrust e56e5eb）
- 新增 `site_state()` / `app_pool_state()`（实时单对象 `appcmd list site|apppool <name>` 文本解析，不走缓存）。
- `stop_site/start_site/stop_app_pool/start_app_pool` 统一走 `change_state()`：命令失败一律用实时状态复核，达到期望状态即视为成功。
- `appcmd` 错误消息带**命令**与**当前状态**（便于定位权限/名字问题）。
- `parse_state_line` 同时兼容 `state:`（站点小写）与 `State:`（应用池大写）。

## 修复（DHDeploy Agent v1.0.37）
- `stop()`：停站点失败**不阻断**（维护页 + 停池 + 定向杀 w3wp 才是释放文件的关键）。
- `start()`：启池失败仅告警、继续启站点；启站点失败才返回错（带阶段前缀）。
- `wait_site_started` 改 `iis::site_state()` 实时轮询（500ms），避开 15s 批量缓存滞后。

## pek-ragent-instance.md

# Pek.RAgent 重复影子实例与单实例锁（2026-10-21，v0.1.50）

## 现象（用户线上 Windows）
- 应用 `dhdeploy-agent-rust` 每约 30 秒被 RAgent `重新部署`，日志：
  - 启动成功 PID=37712 → 30 秒后「进程已退出」→ 30 秒后重新部署；
  - 应用日志 30 秒仍在写 `[Job:CheckSite]`（但那是旧实例）。
- 端口表显示 8282/8283 的监听者：`dhdeploy-agent-rust.exe (33900)`，路径 `D:\Stardust\shadow\dhdeploy-agent-rust-6087191b\dhdeploy-agent-rust.exe`。
- RAgent 新拉起的 PID 不是 33900；33900 是**旧影子实例**，一直存活占着端口。

## 根因
1. 影子目录共用一个 exe；旧代理/旧版本遗留的进程未被清理，仍监听 8282/8283；
2. RAgent 只跟踪自己当前 `Child`，不知道 33900（state/接管未覆盖），再次启动新实例；
3. 新实例监听 8282/8283 失败 → `main` 监听错误分支 `exit(1)`；
4. RAgent 30 秒守卫周期后再拉，旧实例不死 → 无限循环。
- **注意**：应用日志看起来“退出后仍在写”，实际是多个实例写同一个日志文件；`实际运行=31s` 是守卫检测时间，不一定是新实例真实寿命。
- **不是 WAF/CheckSite/外部程序占用**；端口占用者就是应用自己的旧实例。

## 修复（v0.1.50）
- `src/app.rs::start()`：非任务模式、`prepared.run_file` 存在时，启动前扫描系统进程：
  - 精确匹配 `run_file`（canonical path，Windows 大小写不敏感）；
  - 或匹配同一 `shadow_base` 下 `{app}-*` 目录中的进程（覆盖旧 MD5 影子）；
  - 多个匹配：优先保留**有监听端口**的，其次最早启动的；其余 `stop_process`；
  - 保留者直接 `adopt(pid, name)`（Handle::Adopted），**不再 spawn 新实例**。
  - 任务模式不做接管（允许一次性并发）。
- `src/agent.rs::run_core()`：新增 `Data/agent.lock` 单实例锁：
  - `create_new` 原子创建；已有 PID 且 `sys::is_alive` → 拒绝启动并记日志；
  - 进程已退出视为残留锁，清理后重试；正常退出释放（`release_instance_lock`）。
- 回归测试：`shadow_matcher_covers_old_hashes_and_ignores_other_apps`、`same_exe_matches_current_process_binary`；总计 **163 通过**。
- 包：`dist\pek-ragent-v0.1.50-x86_64-pc-windows-msvc.zip`；RAgent v0.1.49 端口表「应用/路径」是诊断入口。

## 运维止血（已给用户）
1. 只保留一个 RAgent（停手动 `-run`/菜单实例，保留服务）；
2. 停 RAgent 服务 → 杀掉所有 `dhdeploy-agent-rust.exe`（含 33900）→ 启动 RAgent；
3. 验证 `Get-Process dhdeploy-agent-rust` 只有一个且 8282/8283 的 PID 与 RAgent 最新 PID 一致。

## proc-top.md

# 进程 Top 字段（2026-10-20）

- `dhrust::sys::monitor::ProcItem`：`name/pid/memory_mb/threads/cpu_seconds` + `cpu_percent/user/exe/command/cwd/handles/start_time`。
- CPU%：两次调用差分，占**单核**可 >100；`Δt < 200ms` 时**复用上次 percent**（否则连续调用全 0）；首次为 0。
- 性能：先全量取轻字段（Linux stat/statm、Windows Toolhelp）排序，只对返回的前 N 补重字段。
- Linux 重字段：`/proc/{pid}/{exe,cwd,cmdline,fd}` + `status` 的 `Uid`→`/etc/passwd`（缓存）；启动时间 = `btime + starttime/CLK_TCK`。
- Windows 重字段：`QueryFullProcessImageNameW`、`GetProcessHandleCount`、`GetProcessTimes`（启动时间）、`OpenProcessToken`+`LookupAccountSidW`（用户名）；无 PEB 读取 → `command` 用 exe 路径、`cwd` 空。
- RAgent：`/star/machine` 返回「CPU Top20 ∪ 内存 Top20」；`/star/getProcessList?sort=cpu|memory&count=N`（N ≤ 300）；前端进程表 7 列可切换排序。

## watchdog.md

# 子服务假死自愈（2026-10-20）

- 症状：RAgent 面板显示「运行中」，但子服务（如 DHDeployRust）请求全无响应；重启 RAgent 才恢复。
- 根因：守护循环只判 PID 存在；`HealthCheck` 只在启动时探一次且失败仅记日志。
- 现实现（`app.rs::check_health`，每 `GuardPeriod` 一轮）：
  - 连续 3 次失败（`HEALTH_FAIL_LIMIT`）→ 停止 + 按 `Delay` 重启；启动宽限 `max(StartWait,5s)`。
  - `HealthCheck` 取值：
    - 空 → 自动发现该进程（含子进程树）TCP LISTEN 口（Linux `/proc` fd→socket inode↔`/proc/net/tcp`；Windows `GetExtendedTcpTable`）+ 宽松探活（写 HTTP 请求，3s 无任何字节 = 假死）。
    - `http(s)://` / `tcp://` → 显式。
    - `file:<路径>[?within=秒]` → 文件活性（mtime+size 无变化）。
    - `heartbeat[?within=秒]` → `POST /star/appHeartbeat?name=`；**从未上报不判定**（不支持则不探）。
    - `off`/`none` → 关闭。
- 原则：拿不到活性信号就不判定（防误杀纯计算型/空闲服务）。
- 面板：`/star/services` 返回 `Health`(off/ok/warn/fail)/`HealthFails`/`HealthError`/`HealthOkAt`/`LastHeartbeat`。
- 测试：`app::tests` 5 项（含「只 listen 不 accept」假死模型）。

## 约定与坑

- zig 缓存重定向：`.cargo/config.toml` `[env]` 的 `ZIG_GLOBAL_CACHE_DIR`/`ZIG_LOCAL_CACHE_DIR`（`relative=true`）→ `target\zig-cache`；`CARGO_ZIGBUILD_CACHE_DIR` 0.23.4 不采纳（残留 `%LOCALAPPDATA%\cargo-zigbuild` ~8MB，脚本 `-Clean` 会清）
- 交叉编译时 zig 输出 `ignoring deprecated linker optimization setting`：无害提示
- **改 unix 代码后必须跑一次** `cargo zigbuild --release --locked --target x86_64-unknown-linux-musl` 验证：本机默认只编 Windows，unix 分支曾潜伏编译错误（pre_exec 闭包需 `Ok(())`、信号处理 `as *const () as usize`、cfg_attr(dead_code)）
- dist 中出现**无扩展名的同名目录** = 手工解压 tar.gz 的残留（打包脚本从 `target/{t}/release` + `packaging/install.sh` 直接打包，不产生 staging 目录）；可安全删除
- Windows 侧 exe 自检（验证版本）：先设 `PEK_RAGENT_BASE=<临时目录>`（否则会在 exe 所在目录生成默认配置），再运行 `target\release\pek-ragent.exe -selftest` → 输出 `selftest ok（vX.Y.Z）`
- 多平台支持规划：`docs/platform-support.md`（国产化 Linux / 嵌入式路由系统 OpenWrt·Buildroot / macOS）；交叉产物已打通 x86_64 / aarch64 / **riscv64(RISC-V)** / **loongarch64(龙芯)**；`-Targets` 支持多选；新增架构只需 `$linuxTargets` 加一行
- 多 init 支持（2026-10-01）：`src/service/` 下 linux.rs（探测分发）/ procd.rs / sysv.rs / inits.rs（模板+决策，带单测）；探测顺序 systemd→procd→SysV，`PEK_RAGENT_INIT` 可强制；22 项测试全绿；待实机验证（OpenWrt x86 虚拟机起步）
- **Linux 服务安装首验翻车与内置自诊断（2026-10-01，用户服务器报 "Unit StarAgent.service has a bad unit file setting"）**：
  - **根因（内置诊断首次实战确认）**：`WorkingDirectory="/www/Agent"` —— **systemd 不剥离 `WorkingDirectory=` 的引号**（把引号当路径本体 → `verify` 报 "path is not absolute" → 单元 fatal 拒启；注意 `ExecStart=` 是剥引号的，两者语义不同）。修复：`WorkingDirectory` **恒裸写**（含空格也不能引号）、`ExecStart` 按需引号（`quote_path`）；含空格路径回归测试；全量文本断言锁定
  - unit 模板同时收紧：ASCII、无注释、无 OOMScoreAdjust（待诊断确认发行版兼容后再评估引入）；`KillMode=process` 保留
