## 2. 项目定位与关键事实
- Pek.RAgent＝星尘代理 Rust 实现（crate `pek-ragent`；GitHub `RemoteAll/Pek.RAgent`，分支 `main`）。
- Windows 服务名 `StarAgentRust`（与 C# StarAgent 5500 并存，默认端口 **5501**）；配置 `Config/StarAgent.config`（XML，与 C# 双端互通）。
- **影子模式（默认部署模式）**：单文件程序复制到 `shadow/{名称}-{md5前8位}/` 运行；源文件不被占用，覆盖源文件 → 5s 检测 → 重建影子 → 自动重启（覆盖升级惯例）。
- **停止链**：温和（Windows `taskkill /PID /T`；Unix 组长按进程组 SIGTERM）→ 3s → 强制（`/T /F`；SIGKILL）→ 2s → 终检（`is_alive` 查 `GetExitCodeProcess`）。
- **多实例**：配置按名称 upsert（不能同名）；多实例用不同子服务名注册，各自目录/配置；停止按 PID，无同名连坐。
- 版本标记 `PEK_RAGENT_VERSION_TAG`（`Pek.RAgent/<版本>`）**禁止删除/改名**（Pek.RPanlServer 发行识别依赖）。

## 3. 构建 / 测试 / 打包
- 工具链：rustc 1.98（x86_64-pc-windows-msvc；交叉 x86_64-unknown-linux-musl 等）；edition 2024。
- 依赖（path，相对 `../`）：`dhrust=../DH.RustBase`、`pek-rcode=../Pek.RCode`、`pek-radmin=../Pek.RAdmin`——**编译报缺 API 时先拉新这三库再复测**。

## 8. 变更记录（2026-10-20）：面板登录会话持久化 + 密码不明文传输

**用户原话**：「RAent的登录是只要重启就要重新输入密码吗?这个能不能做成不要动不动的就被影响到要重新输入密码。因为这个不太可能直接用https的，那么多次输入很容易被截取」

**问题定位（三处叠加，故「动不动就要重输」）**：

1. `WebPanel` 的 `TokenStore` 是**纯内存表**，进程重启（自升级、覆盖部署、服务重启）即清空 → 全部 401；
2. 有效期写死 **24 小时**（`TokenStore::new`）；
3. 前端令牌存 **`sessionStorage`**，关浏览器/标签页即丢。

**改动（共享库 + 本仓 + 前端）**：

- **DH.RustBase**（`src/net/panel_auth.rs`，仅新增、向后兼容）：`ttl_ms()`、`clear()`、`revoke_all_except(keep)`、`touch(token)`（滑动续期：剩余不足一半才续）、`snapshot()` / `restore()`（落盘与重启恢复，容量上限 512）；新增 2 项单元测试。
- **本仓**：
  - 新增配置 `WebSessionHours`（默认 **12 小时**；`0` = 关闭持久化退回进程内 24h；上限 8760 小时；旧键 `WebSessionDays` 兼容读取并按天换算），写入 `Config/StarAgent.config` 模板与配置页；**改值需重启服务生效**（TTL 在 `WebPanel::new` 读取；重启不会掉登录）；
  - 会话落盘 `Data/panel-sessions.json`（`{version,updatedAt,sessions:[{token,expire,principal}]}`，临时文件 + rename 原子替换，Unix 0600），启动 `load_sessions()` 恢复；
  - `principal()` 命中令牌时 `touch` 续期，改动才落盘（12 小时 TTL 下约每 6 小时一次写盘）；
  - **挑战式登录**：`GET /api/loginChallenge?user=…` 下发一次性 `nonce` + 盐（内置管理员用固定虚拟盐 `staragent-builtin`，数据库用户取库中 salt），前端本地算 `SHA-256(nonce : SHA-256(salt:password))` 提交；nonce 一次性、2 分钟过期；**保留明文口令分支**（旧前端/脚本兼容）；
  - `POST /api/logoutAll`（仅内置管理员，保留当前会话）；改密码 / 改用户 / 删用户立即撤销其它（或该用户）会话；
  - 前端：令牌按「保持登录」存 `localStorage`（默认勾选）或 `sessionStorage`，启动两者兼容读取；自带纯 JS SHA-256（http 非安全上下文没有 `crypto.subtle`）；挑战接口不可用时自动回退明文；用户页新增「🚪 退出所有设备」。
- **口径**：令牌 TTL 由配置决定，**滑动续期**——期间用过面板就不掉线；会话文件等同长期凭据，权限 0600、随 `Data/` 目录归属服务账户。
- **已知取舍**：DB 用户权限快照在会话期内不随库实时变化（改用户/删用户已主动吊销）；`WebSessionHours=0` 可完全回到旧行为。

**验证（本机实跑）**：

- `cargo check --all-targets` exit=0；`cargo test`：**136 passed / 0 failed / 1 ignored**；
- DH.RustBase `cargo test --features net --lib panel_auth`：**10 passed**；
- 真实 HTTP 冒烟（临时目录 `-run` + `WebAuthLevel=Full`，改配置后重启进程）：
  `challenge code=0` / `login code=0` / `replay-nonce=401` / `wrong-password=401` /
  **`status-after-restart code=0`（重启后旧令牌仍有效）** / `session-file=True` /
  `logoutAll=0 已退出 1 个其它会话` / `other-token-after-logoutAll=401 current-token=0` / `session-count=1 version=1`；
- 前端 `node --check web/app.js` 通过；`sha256Hex` 与 Node `crypto` 对拍（`abc`/空串/NIST 向量/中文 UTF-8/1KB）一致。

**后续调整（同日）**：用户原话「默认 12小时滑动吧，」——会话保持由「天」改为「小时」粒度：配置项更名 `WebSessionHours`（默认 **12**，上限 8760），配置页/模板/前端说明同步；旧键 `WebSessionDays` 仍可读（按 ×24 换算），避免已落盘的旧配置失效。

## 9. 变更记录（2026-10-20）：进程 Top 对齐 htop / 云监控

**用户原话**：「Agent为什么不能像这种一样的拿到哪个占用资源最高的，要有对应的文件目录以及进程等。」（配 htop 与阿里云「进程监控」截图）

**原有差距**：`dhrust::sys::monitor::ProcItem` 只有 `name/pid/memory_mb/threads/cpu_seconds`——没有瞬时 CPU%、用户、命令行、可执行文件路径、工作目录、句柄数；`getProcessList` 的 `handleCount` 恒 0、`startTime` 恒空。

**改动**：

- **DH.RustBase**（`sys/monitor.rs`）：`ProcItem` 新增 `cpu_percent / user / exe / command / cwd / handles / start_time`；
  - CPU% 由**两次调用的累计 CPU 时间差分**得到（Δt < 200ms 不计，首次为 0），口径「占单核百分比、可 >100」，与 htop/云监控一致；
  - 先全量取轻字段排序，**只对返回的前 N 个**补重字段（Linux `/proc/{pid}/{exe,cwd,cmdline,fd}` + `/proc/{pid}/status` 的 Uid→`/etc/passwd`；Windows `QueryFullProcessImageNameW` + `GetProcessHandleCount` + `GetProcessTimes`）；
  - Linux 启动时间 = `btime + starttime/CLK_TCK`；Windows 由 FILETIME 换算；取不到的留空。
- **本仓**：`machine()` 返回「CPU Top20 ∪ 内存 Top20」（前端可切换排序，避免单一口径盲区）；`getProcessList?sort=cpu|memory&count=N`（上限 300）共用 `process_json()`；前端进程表改为 7 列（PID/用户/进程+可执行文件/CPU%/内存/线程·句柄/启动时间），命令行与工作目录放 `title` 悬浮。
- **限制**：Windows 无 PEB 读取，`command` 用可执行文件路径、`cwd` 为空；Linux 下 `handleCount` 是「打开的 fd 数」（与云监控「打开文件数」同义）。

**验证**：DH.RustBase `cargo check` 通过；`cargo zigbuild --target x86_64-unknown-linux-musl --release` 通过；
本仓 `cargo test` **136 passed**；Windows 端真实 HTTP 冒烟 `rows=32 withExe=31 withUser=31`，
CPU Top：`Code 91.3%` / `Code 77.9%` / `WmiPrvSE 52.4%`，句柄数与启动时间均有值；
`getProcessList?sort=cpu` 与 `/star/machine` 的 CPU%/用户/路径/句柄/启动时间均正常返回。

## 10. 变更记录（2026-10-20）：子服务「假死」自愈（看门狗 / 探活）

**用户原话**（三轮）：

1. 「目前测试发现在DHDeployRust会假死也就是在RAgent中看状态是启动的但是实际请求以及执行操作是没有效果的，在RAgent后台重启后就正常了。怎么样杜绝这种假死状态」
2. 「有一些应用没有web就单纯是一个应用的怎么办？也有可能都不监听端口号的」
3. 「是不是应该参考DH.NAgent或者DH.NStar等项目增加看门狗功能，由应用来主动往RAgent发心跳或者什么样的，如果看门狗这种则RAgent要判断，如果应用本身不支持看门狗则不判断。」

**根因（为什么显示「运行中」却是死的）**：守护循环 `AppInstance::check()` 只判「进程是否退出 / 内存超限 / 文件变动」，
`HealthCheck` 仅在启动时跑**一次**且失败只记日志——进程活着但死锁/阻塞时，PID 一直在，面板自然一直显示「运行中」。

**改动（本仓）**：把健康检查升级为**周期性探活 + 连续失败自动重启**（`GuardPeriod` 一轮，连续 3 次失败判定假死，
走全局 `Delay` 退避重启；启动后 `max(StartWait,5s)` 宽限期不判定）。探针按 `HealthCheck` 解析：

| 配置值 | 语义 | 适用 |
|---|---|---|
| 空 | **自动发现**该进程（含子进程树）的 TCP 监听口（Linux `/proc` socket inode；Windows `GetExtendedTcpTable`），宽松探活：连上后 3 秒无任何字节 = 假死 | 有端口的服务，**零配置** |
| `http(s)://…` / `tcp://…` | 显式地址（HTTP 最准；TCP 只验端口） | 明确知道健康接口 |
| `file:<路径>[?within=秒]` | 文件活性：窗口内日志/输出/DB 文件无变化 → 假死 | 无端口、定时任务/队列型 |
| `heartbeat[?within=秒]` | 主动心跳：应用调 `POST /star/appHeartbeat?name=<应用名>`；**从未上报过 → 不判定** | 可改代码的自有应用（对齐 DH.NAgent / DH.NStar 看门狗） |
| `off` / `none` | 关闭探活 | 明确不想探 |

- 面板：子服务「状态」列在运行中旁边显示「探活异常 n/3」「探活失败」（悬浮看原因）；接口新增
  `Health`（off/ok/warn/fail）、`HealthFails`、`HealthError`、`HealthOkAt`、`LastHeartbeat`。
- 设计原则：**拿不到任何活性信号就不判定**（纯计算型应用不做假死判定，宁可漏判不误杀）。

**验证**：`cargo test --bin pek-ragent app::tests` 5 项通过（含「只 listen 不 accept」的假死模型、
文件活性停滞后判定、心跳未上报不判定、目标解析）；其余全量测试保持通过。

## 12. 变更记录（2026-10-20）：进程列表显示监听端口 + 探活开销下限流

**用户原话**：

1. 「这里是否需要把如果有监听端口号的也给显示出来？」（配进程 Top 截图：三个 `dotnet` 都是 `/usr/share/dotnet/dotnet`，无法区分谁在服务哪个端口）
2. 「RAgent也要考虑性能和资源占用哦，不能自己反而成了资源消耗和消耗的源头了」

**改动**：

- **DH.RustBase**（`sys/monitor.rs`）：`ProcItem` 新增 `ports: Vec<u16>`（TCP **LISTEN**，升序去重）；
  新增 `listen_ports_many(&[u32])` 与 `listen_ports_of(pid)`（含子进程树，供自动探活）。
  - **只扫目标 pid**：Top20 就只看这 20 个进程的 `/proc/{pid}/fd`，**不遍历全系统**（原实现为了找归属会把 `/proc/*/fd` 全扫一遍）；
  - Linux：`/proc/net/tcp{,6}` 取 LISTEN 的 `socket inode → 端口`，再按 pid 反查；Windows：`GetExtendedTcpTable` **一次取全表**（含 IPv4+IPv6）再按 pid 过滤；
  - 2 秒快照缓存（面板 3 秒刷新；缓存已覆盖请求 pid 时直接复用）。
  - **实现下沉**：`Pek.RAgent/src/sys.rs` 原先自带的那份 `listen_ports_of` 删除，改为 `pub(crate) use dhrust::sys::monitor::listen_ports_of;`——进程表与探活共用同一份快照，避免两套实现口径漂移。
- **本仓（性能）**：
  - 健康检查**节流**：守护循环 1 秒一跳，此前**每秒**对每个应用发一次 HTTP/TCP 探活（自动模式还要每秒读一次 `/proc` 端口表）→ 改为 `HEALTH_INTERVAL = 10s`（每应用最多 10 秒探一次，连续 3 次失败仍在约 30 秒内判定假死）；
  - 探活读超时 3s → **2s**（守护线程串行执行 `check_all`，单个应用卡太久会拖慢其它应用调度）。
- **前端**：进程表新增「监听端口」列（`:8080 :443`；不监听显示 `—`），与「当前由哪个应用在服务哪个口」直接对照。
